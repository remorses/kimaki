Join the **Kimaki voice** channel and talk. A realtime voice model answers, and it controls your coding agents with the `kimaki` CLI: it lists threads, reads them, and starts new ones for real work.

```diagram
  you ──voice──▶ Kimaki voice ──▶ realtime model ──shell──▶ kimaki send / session list / read
                     ▲                  │
                     └────── speech ────┘   text chat: transcripts, tool lines, links
```

> A **thread** and a **session** are the same thing: each Discord thread has one OpenCode session. Say either word in a call. The CLI commands say `session` and take thread IDs too.

## How it works

1. Kimaki creates one **Kimaki voice &lt;machine&gt;** channel per computer, outside any category. Drag it where you want.
2. You join it. Kimaki joins too, greets you, and listens.
3. You ask for something. The model runs `kimaki` commands in the Kimaki data folder (`~/.kimaki`).
4. For coding work it starts a thread with `kimaki send --wait` in the background, in the right project channel, and adds everyone in the call to it.
5. When the thread finishes, the model gets its transcript and tells you what it did.
6. The call ends when the last user leaves, or when you ask the model to hang up.

## The text chat

Every Discord voice channel has a **text chat**. Kimaki uses it to show the call:

- your words as `» tommy: ...` and the model's answers
- each command the model runs, like `┣ shell kimaki session list`
- links and IDs the model posts, so it never reads them aloud
- files from `kimaki upload-to-discord`, which posts here when called during a call

Type in the chat to talk to the model without speaking.

## What to ask

```text
Which threads are running now?
Start a thread in the website project to fix the broken signup link.
What was the last thread about the parser?
```

## Threads report back

The model starts every thread with `--wait` as a background command:

```bash
kimaki send --channel <project channel> --prompt 'Fix the broken signup link' --user <you> --wait
```

The thread shows in the text chat at once, and you can keep talking. When the thread finishes, the same command returns its transcript. So the model gets the notification and the result together, and tells you what the thread you just started did, with no extra `kimaki session read`.

Other slow commands like `kimaki session wait` also run in the background.

## Finished thread notifications

When a thread of **any** project finishes or fails during a call, Kimaki posts a line in the text chat with the title, the thread link and the session ID:

```text
⬦ thread finished: Fix signup link ⋅ https://discord.com/channels/<guild>/<thread> ⋅ ses_abc123
```

The model gets the same notice, so it never needs to poll `kimaki session list`:

| Thread | What the model does |
| --- | --- |
| started in the call | tells you it finished |
| started in the call with `--wait` | waits for the transcript, then tells you the result once |
| started elsewhere (Discord, another agent) | keeps it as context, mentions it when you ask |

## Setup: an API key

Voice calls use the same keys as [voice messages](./voice). Add one with **`/transcription-key`** or from a terminal:

```bash
kimaki bot keys set --openai sk-...
kimaki bot keys set --xai xai-...
kimaki bot keys set --gemini AIza...
```

Kimaki picks the first key it finds, saved key before environment variable:

| Provider | Model | Web search |
| --- | --- | --- |
| OpenAI | `gpt-realtime-2.1` | `web_search` tool, runs a `gpt-5.5` web search with the same key |
| xAI | `grok-voice-think-fast-2.0` | built in (`web_search`, `x_search`) |
| Gemini | `gemini-3.8-live` | built in (Google Search) |

Only users who can use Kimaki (server owner, administrators, Manage Server, or the "Kimaki" role) are heard.

## Choose the voice

Each provider has its own **default voice**. The first line of a call shows the model and the voice: `⬦ voice call started ⋅ gpt-realtime-2.1 ⋅ marin`.

| Provider | Default | Other voices |
| --- | --- | --- |
| OpenAI | `marin` | `cedar`, `alloy`, `ash`, `ballad`, `coral`, `echo`, `sage`, `shimmer`, `verse` |
| xAI | `eve` | `ara`, `rex`, `sal`, `leo` and the rest of the [xAI voices](https://docs.x.ai/developers/model-capabilities/audio/text-to-speech#voices) |
| Gemini | `Puck` | `Kore`, `Charon`, `Zephyr` and the rest of the [Gemini voices](https://ai.google.dev/gemini-api/docs/speech-generation#voices) |

Pass **`--voice`** when you start Kimaki:

```bash
kimaki --voice cedar      # OpenAI voice
kimaki --voice Kore       # Gemini voice; names are case-insensitive
kimaki --voice default    # back to the provider default
```

An unknown name stops the start with the full list of voices. The running bot keeps running.

The voice also **picks the provider**. Voice names never repeat across providers, so `--voice Kore` uses Gemini when a Gemini key is set, even if an OpenAI key is set too. Without a key for that provider, the call uses the usual key order (OpenAI, xAI, Gemini) with that provider's default voice, and the text chat says why.

### The voice is saved

Kimaki saves the voice in its SQLite database (`~/.kimaki/kimaki.db`). Pass the flag **once**; you do not need it again:

| Event | Voice |
| --- | --- |
| `kimaki restart` | kept |
| bot crash, computer reboot | kept |
| autostart when OpenCode starts (`~/.kimaki/autostart.command`) | kept |
| `kimaki` with no `--voice` | kept |
| `kimaki --voice <other>` | replaced |

The precedence is: `--voice` flag, then the saved voice, then the provider default. The autostart script does not need to change: it reads the saved voice like any other start. Each data directory (`--data-dir`) has its own voice.

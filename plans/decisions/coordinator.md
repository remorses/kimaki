- Workers are `kimaki send` threads, not `subagent` children: they reuse all thread code, work in other projects and worktrees, and users can talk to them. The `subagent` tool stays allowed, only for blocking throwaway work the user never sees (explore, lookups).
- A finished thread run sends the coordinator a synthetic `<session-finished>` item like OpenCode's subagent completion. `resume: true` only when the coordinator started it (`--parent-session`); threads of the channel and routines get `resume: false`.

Only a run whose prompt a coordinator sent (start, follow-up, fork) wakes it; a run the user steered in the thread is a silent note with their `<user-prompt>`.

- User, 2026-10-28: "let's remove this feature." Removed the idle nudge ("the user has not replied for N minutes", at half the warming window): it woke the coordinator after the Anthropic prompt cache had expired, so every nudge paid a full cache write only to get `IDLE`.
- User, 2026-10-29: "mainmast session has its own warmup implementation. so that mainmast does its own wamrup while child sessions are running. so when notifications come in they dont trigger a kv cache write. and so we can disable the warmup global ... limit this to max 1.5 hours". The plugin sends OpenCode-style `session.generate` keep-alives (same prompt and 4-minute interval as OpenCode's warming) to the coordinator while its channel is busy, at most 1.5 hours after its last real request. Global `warming` is no longer needed.
- (agent) "Busy" (the coordinator or a thread of its channel runs and does not wait for the user) comes from the bot's thread views through the `session.warmup` lock route (was `coordinator.busy`): the plugin cannot list sessions or their run state. The request timing stays in the plugin, because only its hooks see the exact request times that the cache TTL counts from.
- (agent) Warmup only keeps a warm cache warm: it starts at a real coordinator request, never later. A thread the user starts hours later does not rewarm a cold coordinator.
- (agent) When the warmup ends (channel idle, or the cap) the plugin compacts the coordinator if the last request used at least 100k tokens, while the cache still holds. Not a share of the window: a day-long coordinator at 190k never reached 20% of a 1M window. The warmup also lives in plugin storage (`ctx.storage`), because OpenCode reloads the plugin on every Kimaki build and that cleared the timers.
- User, 2026-11-03: "we have a plugin that does warmup for coordinator. lets do something similar for sleep. for max sleeps of 2 hours." The same warmup also keeps any root Kimaki session warm while it waits for a `kimaki sleep` wake, when the sleep is at most 45 minutes long (wake time minus sleep start, bot clock). User, 2026-11-03, after the cost note: "Lower cap to 45m": past about 45 minutes the keep-alives (0.1x input each, every 4 minutes) cost more than one cache write at the wake (1.25x). The bot answers `sleeping` in `session.warmup` (`sleepsWarm` in `sleeps.ts`); the 1.5-hour cap applies only to busy channels. Only coordinators compact when their warmup ends.
- (agent) `IDLE` stays visible in the OpenCode TUI. OpenCode v2 has no flag to hide assistant text (the TUI only hides empty text parts and synthetic messages without description), and TUI plugin slots do not cover message rows. Rewriting the provider response in `http.response` would be a hack.
- (agent) `kimaki session read` defaults to prompts and final answers; `--full` shows tool calls.

The coordinator and worker role texts come from the `kimaki` plugin, derived from markers (coordinator: `threadId === channelId`; worker: `parentSessionId` or fork chain reaches a coordinator). OpenCode has no plugin instruction source, so the text is a synthetic message stored before a user prompt when the latest one is missing or stale (like OpenCode's plan plugin); a wake with no prompt gets it on its last user message for that request only.

- User, 2026-10-31: "tell to only do for prompts that will take more than 5 seconds. so we are less noisy. lets do this adding support for a --wait 5". Every coordinator `kimaki send` uses `--wait 5`. A run that ends within it is reported from the command output; a follow-up still running after it gets one notice line with the thread link. The prompt metadata stores the wait deadline (`waitUntil`), so a run that outlives the wait still sends its note even when the coordinator is busy.
